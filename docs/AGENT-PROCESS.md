# 多 Agent 协作开发流程（权威，v1.0）

> 本文件定义本项目**每一轮开发任务**的固定流程：从需求输入到测试窗口验收再到提交发布。
> 本流程是**用户与总管（主 Agent）之间的协作契约**，每轮任务必须完整走完闭环，
> 不得临时发挥、不得跳过测试窗口验收环节。
>
> 配套：`docs/HANDOFF.md`（技术交接）、`docs/ARCHITECTURE.md`（架构）、
> `docs/BUILD.md`（构建）、`docs/INSTALL.md`（安装）、`VERSION.md`（版本登记）。

---

## 0. 角色与分工

| 角色 | 职责 |
|---|---|
| **用户（验收人）** | 输入需求 → 确认验收标准 → 在测试窗口实测 → 裁定"通过/不通过" |
| **总管（主 Agent）** | 需求确认、拆解任务书、派发、集成核对、构建、**弹测试窗口**、提交发布、防卡死兜底 |
| **Agent A（代码）** | `KeyDisplay.Widget/`（UWP C# 渲染/交互/布局） |
| **Agent B（伴生）** | `KeyDisplay.Companion/`（Python 钩子/管道/性能）+ 测试回归 |
| **Agent C（构建打包）** | `installer/`、`dist/`、release 归档、版本号三处同步 |
| **Agent D（文档质量）** | `docs/`、`README.md`、`VERSION.md`、静态审查、交接同步 |

> 4 个 Agent 固定使用免费模型（`opencode` 路由的 `deepseek-v4-flash-free`），
> 由总管在派发时钉死 provider/model，不消耗用户付费额度。

---

## 1. 流程闭环（每轮任务完整走 ①→⑥）

```
① 需求输入         用户一句话描述目标（功能/修复/优化）
     ↓
② 验收标准确认     总管复述理解 + 列出"可被证明的验收点"，用户确认后才继续
     ↓
③ 拆解 + 派发      总管写任务书（自包含：路径/背景/验收标准），4 Agent 并行执行
     ↓
④ 集成 + 自检      总管核对 git diff、编译、单测、静态审查
     ↓
⑤ 构建 + 测试窗口  总管构建两端 + 自动弹出测试窗口，并说明"看什么、怎么操作"
     ↓
⑥ 用户验收         通过 → 提交/发布 ✅ ；不通过 → 用户反馈 → 回到 ③
```

### 各阶段规则

**① 需求输入**
- 用户一句话即可，无需懂技术细节。
- 总管只做一件事：把需求翻译成"这个项目里改哪里、影响什么"。

**② 验收标准确认（重要，防返工）**
- 总管输出 2~5 条**可验证**的验收点，例如：
  - "悬停 Q 键右缘，光标变成左右拉伸箭头（SizeWestEast）"
  - "锁定开关打开后，拖拽按键无效"
  - "伴生进程单测 21/21 通过"
- 用户说"对"才进入③；用户补充/修改则改完再确认。
- **验收标准里必须包含至少 1 条可在测试窗口里亲眼看到的效果**（除非纯后端改动）。

**③ 拆解 + 派发**
- 总管把任务切成互不冲突的文件域（每人只碰自己那摊，避免写冲突）。
- 每份任务书自包含：项目根路径、涉及文件、背景、具体任务、完成标准、汇报格式。
- 全部钉在免费模型上并行执行；总管不阻塞等待，边等边做集成准备。

**④ 集成 + 自检**
- 总管亲自 `git diff` 复查每个 Agent 动过的文件（Agent 的汇报不替代总管核对）。
- 代码改动必须编译通过；伴生进程改动必须单测通过；文档改动必须与代码一致。
- 发现质量问题：小问题总管直接修，大问题退回对应 Agent 重做（最多 2 次）。

**⑤ 构建 + 测试窗口（本轮的核心交付）**
- 总管自动完成：构建 widget（如改 C#）→ 构建/部署伴生进程（如改 Python）→ 启动测试窗口。
- 测试窗口启动优先级（自动降级）：
  1. UWP widget 独立窗口：`explorer.exe "shell:AppsFolder\KeyDisplay.Widget_hdjf4fqmxxv8g!App"`
  2. tkinter 开发预览：`python tools\preview.py`（最快看布局/反色，无需重装）
  3. 两者都失败 → 报告失败原因 + 给出手工启动命令，不干等
- 总管必须附上**验收指引**：窗口里看什么、怎么操作、预期什么结果（对应②的验收点）。
- 测试窗口保持打开，等待用户验收；总管不擅自关闭。

**⑥ 用户验收**
- 用户实测后回复："通过" 或 "不通过 + 哪里不对（一句话）"。
- 通过 → 总管按 VERSION.md/发布规则提交（或按用户要求只提交不发布）。
- 不通过 → 总管把反馈翻译成新任务书，回到③（同一轮内迭代，不计新任务）。

## 2. 测试窗口机制（用户核心诉求）

- **每次完工必弹窗口**：任何一轮任务，⑤是强制环节，不允许"改完了但你没看到效果"。
- 窗口弹出时，总管必须给出三行话：
  1. 这是什么窗口（预览 / 真实组件）
  2. 看什么（对应验收点，例如"悬停 Q 键右缘看光标形状"）
  3. 怎么操作（例如"布局解锁后拖拽按键边缘"）
- 纯文档/纯后端改动（无可见效果）时，总管明确说明"本轮无可视效果，验收点为单测/编译通过"，并用日志/测试输出代替窗口。
- 验收不通过 ≠ 任务失败：只是回到③迭代，不产生额外成本。

---

## 3. 防卡死设计（总管必须遵守）

1. **绝不无限重试**：Agent 失败/超时 → 换模型重试 1 次 → 仍失败则串行化（逐个跑）→ 再失败就列问题清单给用户决定。任何分支最多 3 步，必有出口。
2. **验收不阻塞**：用户不在时，总管把窗口开着、构建产物备好、状态写成"等你验收"，不干等不空转。
3. **随时可喊停**：用户可随时打断（消息即中断信号）；总管派出的后台 Agent 均可中断/续派。
4. **疑问只问一次**：能自主决定的小事直接做（沿用 HANDOFF 纪律），只有"验收标准"和"提交/发布决策"必须问用户。
5. **卡住必有状态**：任何一步超过预期时间，总管输出"当前卡在哪 + 你只需要做 X"，不让用户猜。
6. **失败可视化**：编译失败/单测失败/窗口启动失败，都直接贴错误摘要，不隐藏不绕弯。
7. **文件域隔离**：任务书按文件域划分，从源头避免 Agent 之间写冲突（最常见的卡死源）。

---

## 4. 提交与发布规则（沿用 VERSION.md / HANDOFF §6.6）

- 每轮验收通过后，总管询问用户：**只提交** 还是 **升版本完整发布**（三处版本号 + 重建 Setup + 归档 release/ + 提交）。
- 文档类改动不递增版本；功能/修复按 VERSION.md 规则递增。
- 提交信息遵循项目风格（中文、一句话概括、含"修复/新增/清理"动词）。

---

## 5. 每轮任务的工作产物（交付清单）

| 阶段 | 产物 |
|---|---|
| ② | 验收标准清单（用户确认过） |
| ③ | N 份任务书（每份含文件域 + 验收标准） |
| ④ | 集成核对记录（diff 摘要 + 编译/单测结果） |
| ⑤ | 打开的测试窗口 + 验收指引 |
| ⑥ | 用户验收结论 |
| 提交 | git commit（含 release 安装包成对，如发布） |

---

## 6. 变更本流程

- 流程本身需要调整时，由用户提出，总管改本文档后重新提交；
- 流程版本号在本文档标题维护（当前 v1.0）。
